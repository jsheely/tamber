# Tamber mobile

The Tamber app for iOS and Android (Expo SDK 57, React Native 0.86, expo-router). It reads anything
aloud through your self-hosted Tamber server and highlights each word as it is spoken:

- **Share sheet**: share a web page, link, text or document (PDF, EPUB, DOCX, HTML, Markdown, TXT)
  to Tamber from any app. It opens the player and starts reading right away.
- **Compose**: type or paste text, fetch a link (`/v1/extract`), or import a document (upload to
  `/v1/extract`), then press Play.
- **Player**: progressive, gapless playback while the server is still synthesising, karaoke word
  highlighting, tap any word to jump there, previous/next sentence, a queue position while the
  server is busy, background and lock-screen playback.
- **Voices**: search, filter, favourites, audition, and blends of 2 to 4 voices.
- **Library**: the last 20 documents, stored on the device.
- **Settings**: the shared Tamber settings model (server, key, voice, speed, format, chunking,
  highlight, auto-scroll, theme, motion, volume), persisted across restarts.

## Setup

`mobile/` is a pnpm workspace member (see `docs/ARCHITECTURE.md` §9.4 and §12 D12). pnpm's
isolated linker gives it its own `node_modules` with the SDK-pinned React 19.2 and TypeScript 6,
while the web workspaces use React 19.3 and TypeScript 7; nothing is hoisted across packages. It
consumes the shared client as `"@tamber/client": "workspace:*"`, resolved straight from
`packages/client/src` (no build step, see below).

```sh
# from the repo root: one install covers every workspace, including mobile/
pnpm install
```

### Checks

```sh
pnpm exec expo install --check     # dependency versions match SDK 57
pnpm typecheck                     # tsc --noEmit
pnpm lint                          # expo lint (eslint-config-expo, flat config)
pnpm test                          # jest-expo + @testing-library/react-native
pnpm exec expo-doctor              # 21/21
pnpm export:check                  # expo export --platform android; bundles @tamber/client from source. Delete .export-check afterwards
```

Always add native or Expo packages with `pnpm exec expo install <pkg>` so the version is certified
for the SDK (for example, SDK 57 pins `react-native-reanimated` 4.5.1 and `react-native-worklets`
0.10.1). Use a plain `pnpm add` only for pure-JS packages such as `zustand`.

### How Metro finds `@tamber/client`

`expo/metro-config` detects the pnpm workspace root (`pnpm-workspace.yaml`) and configures
`watchFolders` and `nodeModulesPaths` for the monorepo. `metro.config.js` only adds one thing: the
`source` export condition. `packages/client/package.json` lists `"source": "./src/index.ts"` (and
`./src/brand.ts` for `@tamber/client/brand`) ahead of the `dist/` entries, so Metro bundles the
TypeScript source directly, transpiled by `babel-preset-expo` like any app file, and edits under
`packages/client/src` hot-reload in the dev client. Jest maps the package to the same source files
(`moduleNameMapper`), and `tsconfig.json` adds `customConditions: ["source", "react-native"]` so
`tsc` sees the same files.

If a native library ever fails to resolve under pnpm's isolated linker, switch the whole workspace
to Expo's documented fallback by adding `nodeLinker: hoisted` to `pnpm-workspace.yaml` and
re-running `pnpm install`.

## Running the app: a dev client, not Expo Go

Tamber uses native modules that Expo Go does not include (expo-share-intent with its iOS Share
Extension and Android intent filters, react-native-mmkv, the expo-audio background service), so it
runs in a **development build** (`expo-dev-client`).

### Android (fully local on Windows)

Requires Android Studio (SDK + emulator) or a USB-debugging device, and JDK 17.

```sh
pnpm exec expo run:android    # prebuild + gradle + install the dev client, then starts Metro
# later, for JS-only changes:
pnpm start                    # expo start --dev-client (or `pnpm dev:mobile` from the root)
```

`android/` and `ios/` are generated by Continuous Native Generation (`pnpm exec expo prebuild`) and are
gitignored. Configure native behaviour in `app.config.ts` only.

### iOS (EAS Build in the cloud)

iOS can't be built on Windows. Use EAS Build's macOS runners:

```sh
pnpm add -g eas-cli           # or use pnpm dlx eas-cli@latest
eas login
eas build --profile development --platform ios              # dev client for a registered device
eas build --profile development-simulator --platform ios    # simulator build (no share sheet testing)
eas device:create                                           # register an iPhone for internal builds
```

Install the build on the phone, then run `pnpm start` on Windows and open the project from the dev
client (same network, or `pnpm exec expo start --tunnel`). The profiles are in `eas.json`:
`development` (dev client, internal distribution), `development-simulator`, `preview` (internal
release build) and `production` (store). Before the first iOS build, EAS asks to create the bundle
id `net.thirtytech.tamber`, the Share Extension's bundle id and the App Group
`group.net.thirtytech.tamber` in your Apple Developer account.

## Testing the share sheet

- **Not in Expo Go**: the share targets exist only in a development or release build.
- **Android**: install the dev client (`pnpm exec expo run:android`), then share from Chrome ("Share" >
  Tamber), from Files, or with adb:
  `adb shell am start -a android.intent.action.SEND -t text/plain --es android.intent.extra.TEXT "https://example.com/article" net.thirtytech.tamber`
- **iOS**: the Share Extension needs a **real device** with an EAS development build. The cloud
  simulator preview (EAS Simulator) is not confirmed to support share extensions.
- Payload handling: a file is uploaded to `/v1/extract`; a link (or text that is only a link, or a
  page title plus a link) is extracted from the URL, and if that fails the shared title/text is
  read instead; any other text is read directly. Payloads are handled on a cold start and while
  the app is running (`src/share/`).
- If no server is configured yet, the share waits and starts playing when onboarding finishes.

## Configuration

Everything is set in the app (onboarding, then Settings). There are no build-time environment
variables.

| Setting | Stored in | Notes |
|---|---|---|
| Server address | MMKV `tamber.settings` | Normalised with `normalizeBaseUrl` (no trailing `/`, no `/v1`). Use the HTTPS URL of your NetBird (or other) reverse proxy. `http://` works for LAN dev servers (iOS allows local networking only; Android allows cleartext). |
| API key | expo-secure-store `tamber.apiKey` | Keychain / Android Keystore, never in MMKV. Sent as `Authorization: Bearer`. |
| Voice, speed, format, chunking, highlight, auto-scroll, theme, motion, volume, favourites | MMKV `tamber.settings` | The shared `TamberSettings` model, persisted with zustand `persist` (version 1, `migrateSettings` on load, `updateSettings` on every change). |
| Library | MMKV `tamber.library` + `Paths.document/library/<id>.txt` | Last 20 items. |
| Draft text | MMKV `tamber.draft` | Debounced, up to 1 MB. |

App identity (`app.config.ts`): name **Tamber**, scheme `tamber`, bundle id / package
`net.thirtytech.tamber`, App Group `group.net.thirtytech.tamber`. Icons and splash come from
`assets/`, which are copies of `assets/brand/png/*` as `assets/brand/BRAND.md` prescribes.

## How playback works

```
POST /v1/tts (expo/fetch streams response.body; Accept-Encoding: identity)
  start  -> chunk plan: the reader lays out the text; progress segments
  chunk  -> base64 audio  -> File(Paths.cache, tamber/<requestId>/<index>.wav).write(b64, {encoding:'base64'})
         -> AudioPlaylist.add({ uri })           native, gapless queue (AVQueuePlayer / ExoPlayer)
         -> TimelineBuilder.add(chunk, duration) absolute word times
requestAnimationFrame: clock = start(chunk[playlist.currentIndex]) + playlist.currentTime
         -> wordIndexAt(timeline, clock) -> highlight
```

- **Why per-chunk files in an AudioPlaylist**: every NDJSON line carries a complete WAV/MP3 file,
  so each chunk is written as-is and queued. expo-audio's `AudioPlaylist` plays them back to back
  natively, which is gapless for WAV, and there is no MSE anywhere (a test enforces this). The
  alternative, appending PCM to one growing WAV, would need file rewrites and player reloads and
  would break seeking.
- **Seeking**: tapping a word uses `timeForCharOffset`. Audio already received is reached with
  `skipTo` (which starts the track at 0) plus, for a word inside the chunk, `seekTo`. The in-track
  `seekTo` waits until the new track reports `isLoaded`: on iOS `skipTo` builds fresh
  `AVPlayerItem`s, and AVFoundation raises an exception for a completion-handler seek on an item
  that is not `readyToPlay` yet. A chunk up to 2 ahead of the stream is awaited. Anything further away, or
  before the queued run, aborts the request and re-requests with `start_chunk`, reusing cached
  chunks where it can. A change of speed or voice restarts synthesis from the current chunk.
- **Document upload**: SDK 57 makes `expo/fetch` the global `fetch`, and its FormData encoder
  rejects React Native's `{ uri, name, type }` file parts. `src/content/extract.ts` therefore
  sends a part with `name`, `type` and a lazy `bytes()` reader (expo-file-system `File`), which
  that encoder supports. A test runs the real encoder.
- **Background and lock screen**: `setAudioModeAsync({ playsInSilentMode, shouldPlayInBackground,
  interruptionMode: 'doNotMix' })`, and the expo-audio plugin adds `UIBackgroundModes: audio` and
  the Android media foreground service. In SDK 57, `setActiveForLockScreen` exists only on
  `AudioPlayer`, not on `AudioPlaylist`. So a silent, looping "session anchor" `AudioPlayer`
  (`src/player/audioSession.ts`) holds the lock-screen/media-session registration (title, artist
  "Tamber", album = voice). That registration is what keeps Android from killing background audio
  after about 3 minutes. Lock-screen play/pause is mirrored to the playlist. Only real state
  changes are mirrored: reports while the anchor is buffering or not yet loaded (iOS reports
  `playing: false` right after `play()`), and stale reports racing our own play/pause (600 ms
  window, then re-checked against the live state), are ignored. The lock screen shows
  no scrubber, because the anchor's position is meaningless.
- **Aborting**: stop and seeks abort the fetch through a signal bound into the client's `fetch`
  (`src/api/fetch.ts`), so the server stops synthesising immediately.

## Layout

```
app/                  expo-router screens: _layout, index (compose), player, voices, settings,
                      onboarding, library, +native-intent (share deep links), +not-found
src/api/              TamberClient factory + hooks (useVoices, useHealth, connection test)
src/content/          extraction helpers (URL, document upload, stats)
src/player/           StreamPlayer (framework-free), controller singleton, chunk files,
                      lock-screen session, rAF clock hook
src/reader/           paragraph layout, memoised ChunkText, Reader (FlatList, auto-scroll)
src/share/            resolveShareIntent (pure) + root routing effect
src/store/            settings (MMKV + secure-store), library, playback (in-memory)
src/theme/, src/ui/   brand tokens from @tamber/client/brand, Orb, bars, controls, primitives
src/__tests__/        jest-expo tests; __mocks__/ has in-memory expo-audio, expo-file-system,
                      expo-secure-store and react-native-mmkv
```

## Known limitations

- iOS builds and the iOS Share Extension have not been run on a device from this Windows host.
  They need an EAS build and a real iPhone.
- The lock-screen controls offer play/pause only (no scrubbing).
- MP3 chunks use the server's nominal duration for the timeline. Highlighting can drift by a few ms
  per chunk; WAV (the default) is exact.
- Chunk files of the current document stay in `Paths.cache/tamber/` until Stop, a new document, a
  voice/speed change or the next app start (so seeking back never re-synthesises). WAV is about
  170 MB per hour of audio; choose MP3 in Settings for very long documents. The OS may purge the
  cache directory under storage pressure.
